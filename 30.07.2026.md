## ТАКТ 1. РЕЖИССУРА ХАОСА И ГЕНЕРАЦИЯ СЫРЬЯ (PYTHON)

### Шаг 1. Изоляция файловой структуры
*   **Действие:** На жестком диске создана директория `FINTECH_CASE_1`.
*   **Зачем это сделано:** Локализация проекта. В промышленной разработке каждый конвейер изолируется в своей папке, чтобы исключить перемешивание зависимостей и файлов разных бизнес-задач.

### Шаг 2. Развертывание локального сервера Jupyter
*   **Действие:** ЧерезAnaconda Prompt выполнен переход в директорию и запущен сервер: `cd C:\FINTECH_CASE_1` -> `jupyter notebook`.
*   **Зачем это сделано:** Принудительное ограничение прав веб-сервера. Запуск Jupyter строго внутри целевой папки страхует от потери путей и кривого сохранения файлов операционной системой Windows.

### Шаг 3. Подключение вычислительных станков
*   **Действие:** Создан ноутбук `01_data_generator.ipynb`, в ячейке №1 выполнен код:
    ```python
    import pandas as pd
    import random
    ```
*   **Зачем это сделано:** Загрузка ядра Pandas и генератора случайных чисел в оперативную память (RAM) компьютера для последующих матричных трансформаций.

### Шаг 4. Формирование сырых векторов (Тестовая заглушка)
*   **Действие:** В ячейке №2 зафиксированы три несвязанных списка на 5 строк:
    ```python
    tx_ids = list(range(1001, 1006))
    user_ids = [501, 502, 501, 503, 502]
    amounts = [15000, None, -4500, 23000, None]
    ```
*   **Зачем это сделано:** Симуляция ТЗ финансового директора. Пропуски `None` имитируют сбой ИТ-системы, а отрицательное число `-4500` — операцию возврата, искажающую валовую выручку. Создание микро-заглушки позволяет отладить логику без нагрузки на процессор.

### Шаг 5. Сборка и фиксация сырого DataFrame
*   **Действие:** В ячейках №3 и №4 списки упакованы в матрицу и экспортированы на диск:
    ```python
    df = pd.DataFrame({'tx_id': tx_ids, 'user_id': user_ids, 'amount': amounts})
    df.to_csv('raw_transactions.csv', index=False)
    ```
*   **Зачем это сделано:** `pd.DataFrame` жестко сшивает изолированные списки по строкам и индексам. Метод `.to_csv` с параметром `index=False` материализует хаос из RAM в осязаемый текстовый файл на диске, отсекая мусорную нумерацию строк, которая ломает импорт в базы данных.

## ТАКТ 2. РЕЗЕРВАЦИЯ И СТРУКТУРИРОВАНИЕ ДАННЫХ (SQL / СУБД)

### Шаг 6. Запуск автономной СУБД на выделенном порту
*   **Действие:** Запущен пусковой скрипт автоматизации `start_database.bat` (PostgreSQL 16 на порту 5433) и подключен графический клиент DBeaver.
*   **Зачем это сделано:** Переход от текстовых файлов к промышленному стандарту хранения. Локальный порт 5433 изолирует учебный контур от боевых баз системы, исключая аппаратные конфликты.

### Шаг 7. Разметка реляционного сектора хранения (DDL)
*   **Действие:** В редакторе SQL DBeaver выполнена команда разметки:
    ```sql
    CREATE TABLE raw_transactions (
        tx_id INT,
        user_id INT,
        amount NUMERIC
    );
    ```
*   **Зачем это сделано:** СУБД требует строгого описания типов данных до начала загрузки. Тип `NUMERIC` для сумм выбран снайперски — он гарантирует абсолютную точность вычислений копейка в копейку без округлений процессора, в отличие от типа `FLOAT`.

### Шаг 8. Аппаратный сброс кэша интерфейса
*   **Действие:** Выполнено обновление дерева навигатора DBeaver через команду `F5` на папке «Таблицы».
*   **Зачем это сделано:** DBeaver не обновляет структуру папок в реальном времени. Сброс кэша принудительно синхронизирует графический интерфейс с RAM СУБД, материализуя созданную таблицу в навигаторе.

### Шаг 9. Пакетный импорт сырья и верификация (QA Check)
*   **Действие:** Через мастер импорта DBeaver файл `raw_transactions.csv` залит в базу, выполнен контрольный запрос:
    ```sql
    SELECT * FROM raw_transactions;
    ```
*   **Зачем это сделано:** Реализация принципа Zero Trust (Нулевое доверие). Аналитик обязан лично убедиться, что все 5 строк долетели до диска, индексы не съехали, а пропуски `NaN` из Python корректно конвертировались в официальный статус пустых ячеек СУБД — `[NULL]`.
